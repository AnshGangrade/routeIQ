## 1. Project Overview

### 1.1 Problem `[SOURCE]`

Delivery businesses must decide the order in which a driver visits a list of stops (a Vehicle Routing Problem, VRP). Common solutions use fixed, hand-designed heuristics such as **Nearest-Neighbour (NN)** construction and **2-Opt** local search. They are simple and fast, but the same rule is applied to every scenario (dense clusters, spread-out stops, and so on), and designing a better rule for a specific scenario needs an expert and manual tuning.

### 1.2 Proposed solution `[SOURCE]`

Use a **Large Language Model (LLM) as an automated heuristic designer**, inside an evolutionary loop:

1. The LLM proposes a heuristic as executable code (a scoring function that decides which stop to visit next).
2. The heuristic is run on simulated delivery instances and its route distance is measured.
3. The best heuristics are kept, and a structured performance summary is sent back to the LLM.
4. The LLM proposes improved heuristics for the next generation. This repeats for a small, fixed number of generations.
5. The best evolved heuristic is compared with NN and 2-Opt on the same instances.

The research question is deliberately small: *can an LLM-guided evolutionary process find a routing heuristic that beats standard hand-designed ones on these instances?* The answer may be "partly" or "no", and the project reports whichever it is.

### 1.3 Objectives `[SOURCE]`

| # | Objective |
|---|---|
| O1 | Build a classical baseline solver: Nearest-Neighbour construction + 2-Opt local search. |
| O2 | Build an LLM-driven loop that proposes candidate heuristics as executable code. |
| O3 | Build a Heuristic Evaluator that simulates each candidate on synthetic instances and scores total route cost. |
| O4 | Build Fitness Scoring and Selection that keeps the best heuristics and feeds structured feedback back to the LLM. |
| O5 | Compare and visualize the evolved heuristic against baselines (route cost, improvement %, generation-by-generation progress). |

### 1.4 Scope: required vs optional

| Area | `[REQUIRED]` | `[OPTIONAL]` (future improvements) |
|---|---|---|
| Data | Seeded synthetic instances: one depot, N stops, Euclidean distances | Real city coordinates, road distances via a routing service |
| Baselines | NN and NN + 2-Opt | Random-route sanity floor, OR-Tools reference solution |
| LLM engine | Generate, validate, evaluate, select, feedback, small fixed generations | Crossover between parents, diversity prompts, multi-objective fitness |
| Multi-driver `[ADDED]` | K drivers, depot, balanced stop assignment, per-driver route optimization, per-driver and total metrics | Vehicle capacity, time windows, evolving the assignment rule itself |
| Dashboard `[SOURCE]/[ADDED]` | Map, orders, drivers, charts, optimization controls, comparison table | Run history page, export to PDF/CSV, dark mode |
| Reproducibility | Seeds, saved run logs, replay of cached LLM responses | Docker image for one-command setup |

**Out of scope (do not build, do not claim):** live traffic, GPS or driver tracking, real customer data, production-scale logistics, user accounts, mobile app, model training or fine-tuning.

### 1.5 Assumptions

- All data is **synthetic**. Coordinates are generated by the instance generator inside a fictional area.
- Distance is **straight-line (Euclidean)**, not road distance. Cost = total distance of a closed tour: depot → stops → depot.
- One depot. Every stop is visited exactly once.
- The "heuristic" is a **stop-scoring function**. It does not build the whole route itself (see section 5.1).
- Single objective: **total route distance** (the synopsis names one comparison metric).
- Standard laptop, 8 GB RAM, no GPU, internet access for runtime LLM API calls `[SOURCE]`.
- Reconciling the source documents `[ADDED]`: the synopsis frames the core problem as ordering stops for one driver (time windows optional), while the PPT problem statement mentions fleets, capacity, and time windows. This plan keeps the **evolution experiment single-route** (as in the synopsis) and adds **multi-driver routing as a layer on top** (section 6). Capacity and time windows stay optional.

## 5. LLM Evolution Engine

This is the core of the project (synopsis objectives O2 to O5).

### 5.1 What a "heuristic" is `[REQUIRED]`

The LLM writes **one Python function that scores candidate stops**. It does not build routes, return routes, or touch files.

| Item | Specification |
|---|---|
| Function name (fixed) | `score_candidates` |
| Inputs given by the harness | current stop index, depot index, list of unvisited stop indices, the distance matrix (NumPy array), and optionally stop coordinates |
| Output | One number per unvisited stop. **Lower score = visit sooner.** |
| Who builds the route | The **harness** (trusted code): at each step it calls the function, picks the lowest score (deterministic tie-break by stop index), moves there, and repeats until all stops are visited |
| Allowed tools inside | Basic arithmetic and a small set of safe built-ins and NumPy (through a provided `np` name). **No imports.** |
| Style limits | Pure function, no randomness, no global state, no printing, short (about 40 lines or fewer), per-call cost roughly linear in the number of unvisited stops |

**Why this design.** Because the harness picks the next stop, an LLM-written function **cannot produce an invalid route** (a repeated or missing stop) and cannot return a cost the harness would trust. The synopsis describes the heuristic as an "executable scoring function for deciding which stop to visit next", and this design implements exactly that. It also makes safety easier (5.6).

**Sanity anchor.** The function "score = distance from the current stop" is the Nearest-Neighbour rule. It must reproduce the NN baseline exactly (Step 3 test).

### 5.2 The evolution loop `[REQUIRED]`

```
 Start: fixed seed, training/validation/test instance sets, baselines computed
   |
   v
 Generation 0: ask the LLM for K candidate heuristics (no history)
   |
   v
 For each generation g = 0 ... G-1
   1. VALIDATE   each candidate (static checks, then safe test run)  --> reject invalid ones, keep the reason
   2. EVALUATE   each valid candidate on TRAINING instances           --> route costs
   3. SCORE      fitness = mean cost relative to the NN baseline      --> lower is better
   4. SELECT     keep the top E candidates (elites) + best-so-far
   5. FEEDBACK   write a structured summary of what worked / failed
   6. IMPROVE    ask the LLM for K new candidates built from the elites + feedback
   |
   v
 End: re-rank the top few by VALIDATION score, freeze the winner,
      then run it ONCE on the held-out TEST instances against NN and NN+2-Opt
```

**Default budget** (all configurable, kept small as the synopsis requires):

| Setting | Suggested default | Note |
|---|---|---|
| Generations (G) | 5 to 8 | Fixed in advance |
| Candidates per generation (K) | 4 | About 20 to 32 LLM calls per run, plus retries |
| Elites kept (E) | 2 | |
| LLM temperature | Fixed and logged, moderate value | Same value for every run being compared |
| Retries on invalid output | Up to 2 per candidate | Count invalid outputs as a metric |
| Training instances | About 10, sizes 20 to 40 stops | The LLM's feedback is based only on these |
| Validation instances | About 5 | Used only to pick the final winner |
| Test instances | 10 or more per size bucket | **Never shown to the LLM, never used for selection** |

The train/validation/test split is an addition (`[ADDED]`) to the synopsis. It is what makes the final comparison fair (see section 9).

### 5.3 Prompt design `[REQUIRED]`

Every request to the runtime LLM contains:

1. **Task description**: closed delivery tour, one depot, Euclidean distances, goal = shorter total distance.
2. **Exact function contract** from 5.1 (name, inputs, output meaning, forbidden things).
3. **Output format**: one code block containing only the function, plus one sentence explaining the idea.
4. For generations after the first: the **parent code(s)**, their scores, and the **feedback summary** (5.5).

### 5.4 Evaluating and scoring `[REQUIRED]`

- For each instance, the harness builds the route with the candidate and computes its **cost with the project's own trusted cost function**. It never trusts a number reported by the candidate.
- **Normalized score per instance** = candidate cost / NN cost on the same instance. This keeps instances of different sizes comparable.
- **Fitness** = mean normalized score across the training instances. Below 1.0 means better than NN on average.
- **Invalid, crashed, or timed-out candidates** get no fitness and are excluded from selection (their reason is logged and fed back as a "do not repeat" note).
- Also record runtime per instance, because a heuristic that is slow is not comparable with NN on speed.

### 5.5 Selection and feedback `[REQUIRED]`

- **Selection**: keep the best E candidates by fitness, plus a "best so far" record that is never lost.
- **Feedback summary** (generated by the engine, not by the LLM) includes:
  - the elite codes with their fitness;
  - how each did on small vs large instances and clustered vs uniform layouts;
  - the instances where the candidate was **worse** than NN;
  - the rejection reasons seen in the last generation (for example "used a forbidden import");
  - a one-line instruction such as "improve on the worst-case instances without making the best cases worse".
- **Operators**: `[REQUIRED]` initial generation and refine-from-elites. `[OPTIONAL]` crossover of two parents, a diversity-focused prompt, and an explanation step.

### 5.6 Safe validation of LLM-generated code `[REQUIRED]`

LLM output is **untrusted code**. Use several layers; no single layer is enough.

| Layer | What it does |
|---|---|
| 1. Extraction | Take only the code block. Reject replies with more than one function, or with other top-level statements. |
| 2. Static check (AST) | Parse the code without running it. Allow only a whitelist of syntax types (arithmetic, comparisons, loops, simple calls, list/array indexing). **Reject**: any `import`, `global`/`nonlocal`, access to names or attributes starting with an underscore, and calls to `exec`, `eval`, `open`, `compile`, `getattr`, `setattr`, `globals`, `locals`, `input`, `__import__`. Reject code over the length limit. Check the function name and argument names match the contract. |
| 3. Restricted namespace | When the function is created, supply only a small dictionary of safe built-ins (`abs`, `min`, `max`, `sum`, `len`, `range`, `enumerate`, `zip`, `sorted`, `float`, `int`, `round`) and the `np` name. Nothing else is visible to it. |
| 4. Process isolation | Run candidates in a **separate child process**, never in the main app process. Apply a **wall-clock timeout**, a limit on output size, a temporary working folder, and (where the OS supports it) a memory limit. **The child process must not receive the API key or other environment secrets.** |
| 5. Smoke test | Run the function on a tiny instance. Check it returns the right number of finite numbers (no NaN, no infinity, no wrong length). |
| 6. Trusted route building | Because the harness picks the next stop and recomputes cost itself (5.1, 5.4), a candidate cannot corrupt a route or fake a score. |
| 7. Logging | Save every raw reply, the final code, the verdict, and the rejection reason. Show the **validity rate** in the dashboard. |

**Honest limits.** Python-level sandboxing (AST checks plus restricted built-ins) is **defense in depth, not a guaranteed security boundary**. For a local academic demo, process isolation plus timeouts plus no secrets in the child process is a reasonable level. Do not run this on a shared or public server. The stronger `[OPTIONAL]` option is to run the child process in a container with no network, a read-only file system, and CPU/memory caps. Memory limits via the standard library are Unix-only, so on Windows rely on the timeout and, ideally, the container.

**Required safety tests** (Step 4): a sample that imports a module, one that tries to read a file, one with an infinite loop, one that allocates huge memory, one that returns NaN, one with the wrong name, one with an escape attempt using attribute tricks. All must be rejected without hurting the main process.

### 5.7 Comparing against Nearest-Neighbour and 2-Opt `[REQUIRED]`

| Method | What it is | Role |
|---|---|---|
| **Nearest-Neighbour (NN)** | Constructive greedy rule: always go to the closest unvisited stop | Baseline 1 `[SOURCE]` |
| **NN + 2-Opt** | Start from the NN route, then repeatedly reverse route segments while that shortens the tour (fixed iteration cap, run to a local optimum) | Baseline 2 `[SOURCE]` |
| **Evolved** | The frozen best heuristic, building its route with the harness | The method under test |
| Evolved + 2-Opt | Evolved route then 2-Opt polishing | `[OPTIONAL]`, labeled clearly as a hybrid, never mixed into the main comparison |
| Random route | Lower sanity floor | `[OPTIONAL]` |

All methods run on **identical instances and identical distance matrices**.

**Expectation management.** The evolved heuristic is a *constructive* rule like NN, while 2-Opt is an *improvement* step on top of NN and is often a strong baseline. Two separate hypotheses should be reported:

- H1: Evolved is shorter than NN.
- H2: Evolved is shorter than NN + 2-Opt (harder).

The PPT's expected outcome says the evolved heuristic improves over both baselines. In this plan that is treated as a **hypothesis to test, not a promised result**. A negative or mixed result is still a valid, reportable finding.

### 5.8 Reproducibility and demo safety `[REQUIRED]`

- Every run stores: config, all seeds, model name, temperature, prompts, raw replies, validated code, and per-generation scores.
- **Replay mode** re-runs the loop from the stored LLM replies with no API call. The dashboard uses this for demos, so a missing internet connection or an API outage cannot break a presentation.
- LLM output is not perfectly repeatable, so replay is the way to reproduce a past result exactly.

## 6. Multi-Driver Routing `[ADDED]`

The synopsis evolves a heuristic for ordering stops on one route. Multi-driver routing is built as a **layer on top**: split the stops among drivers, then optimize each driver's route with the same methods.

### 6.1 Inputs

| Input | Detail |
|---|---|
| Depot | One shared start/end location |
| Orders | N stops with coordinates |
| Drivers | K drivers (for example 2 to 5) |
| Balance rule `[REQUIRED]` | A maximum number of stops per driver so no driver gets an unreasonable load |
| Capacity, time windows `[OPTIONAL]` | Not required. Add only after everything else works. |

### 6.2 Two-stage method (cluster first, route second) `[REQUIRED]`

**Stage A: assign stops to drivers**
1. Compute each stop's **angle around the depot** (a "sweep").
2. Sort stops by angle and cut the sorted list into K groups, respecting the maximum stops per driver.
3. This is simple, deterministic, and explainable to beginners.
4. `[OPTIONAL]` Alternatives: k-means clustering, or a balancing step that moves border stops between neighbouring drivers if it lowers total distance.

**Stage B: route each driver**
1. Each driver's group becomes a small single-depot instance (depot + that driver's stops).
2. Solve each group with the selected method: **NN**, **NN + 2-Opt**, or the **Evolved heuristic**.
3. Combine the K routes into one plan.

**Key fairness rule:** the **same assignment** (Stage A) is used for all three methods. Then differences in results come from the routing method only, not from different driver groupings.

### 6.3 Where the evolved heuristic fits

- Evolution still runs on **single-route instances** (the clusters-sized problems in 5.2), exactly as in the synopsis.
- The frozen best heuristic is then **applied to each driver's group**. Training instance sizes should therefore resemble typical group sizes (for example 8 to 25 stops).
- Multi-driver test scenarios (for example 60 stops, 3 to 5 drivers) are generated separately and kept out of training.

### 6.4 Outputs and metrics

| Metric | Meaning |
|---|---|
| **Total distance** | Sum of all drivers' route distances (primary metric) |
| **Longest driver route** | Distance of the busiest driver (shows workload imbalance) |
| **Route-length spread** | Standard deviation of driver route distances |
| **Stops per driver** | Count per driver |
| **Improvement %** | Versus NN and versus NN + 2-Opt on total distance |

Because the assignment is fixed across methods, "total distance" is comparable. The longest-driver-route metric is reported but not optimized.

### 6.5 Edge cases to handle

- Fewer stops than drivers (some drivers get none).
- A driver with exactly one stop.
- All stops at nearly the same angle (the sweep groups look odd; the max-stops rule still applies).
- Duplicate coordinates.

## 9. Testing and Metrics

### 9.1 Metric definitions

| Metric | Definition |
|---|---|
| **Route distance (cost)** | Sum of straight-line edge lengths of the closed tour: depot, stops in order, back to depot. Computed by one trusted function used for every method. |
| **Improvement % (per instance)** | `(baseline cost - evolved cost) / baseline cost x 100`. Positive means the evolved route is shorter. Computed separately against NN and against NN + 2-Opt. |
| **Mean and median improvement %** | Average and median of the per-instance values. Averaging per-instance percentages (not averaging raw costs) keeps large and small instances from distorting each other. |
| **Win / tie / loss count** | Number of test instances where Evolved is shorter / within a small tolerance / longer than the baseline. |
| **Normalized score** | Candidate cost divided by NN cost (the quantity used as fitness in the evolution loop). |
| **Generation-wise progress** | Best-so-far training fitness and validation score after each generation. |
| **Valid-candidate rate** | Valid candidates divided by all candidates proposed (an LLM reliability indicator). |
| **Runtime** | Wall-clock time to build a route per method. Reported separately. **The one-time evolution cost (LLM calls, time) is reported separately and not added to route cost.** |
| **Multi-driver metrics** | Total distance, longest driver route, route-length spread, stops per driver (section 6.4). |

### 9.2 Fair-comparison protocol

1. **Same instances and matrices** for every method.
2. **Split** instances into training, validation, and test sets. The LLM sees feedback from training only. The final winner is chosen with validation. The **test set is run once** on the frozen heuristic.
3. **Freeze before testing**: the heuristic's code does not change after test evaluation begins.
4. **Fixed seeds**, all logged. Fixed LLM model and temperature, logged.
5. **Same 2-Opt settings** every time: starting route is the NN route, same iteration cap, run until no improving move.
6. **Repeat the whole evolution** at least **3 times** with different seeds (more if budget allows). Report the **best, mean, and spread** across runs, and never only the best run.
7. **Cover different conditions**: several sizes (for example 20, 40, 80 stops), and both uniform and clustered layouts. Report results by bucket so a win in one condition is not hidden by a loss in another.
8. **Report negative results**. If Evolved does not beat NN + 2-Opt, say so (H2 in 5.7).
9. **Be modest about statistics.** With small test sets, show per-instance paired differences and win/loss counts. A paired non-parametric test (such as Wilcoxon signed-rank) is an `[OPTIONAL]` extra. Do not claim general superiority from a small synthetic benchmark.
10. `[OPTIONAL]` Compare against an OR-Tools reference solution to show how far all methods are from a strong solver.

### 9.3 Test plan

| Test type | What it checks | Tag |
|---|---|---|
| Unit tests: cost and validity | Cost of known tiny tours is exact; a route with a repeated or missing stop is flagged | `[REQUIRED]` |
| Unit tests: baselines | NN is deterministic; 2-Opt never worsens a route; both return valid tours | `[REQUIRED]` |
| Harness anchor test | "Score = distance to current stop" reproduces the NN route and cost exactly | `[REQUIRED]` |
| Safety tests | Malicious and broken samples listed in 5.6 are rejected; main process stays healthy | `[REQUIRED]` |
| Parser tests | Code extracted from replies with extra text, multiple code blocks, or none | `[REQUIRED]` |
| Evolution integration test | Full loop with the mock LLM completes and writes a complete run log | `[REQUIRED]` |
| Reproducibility test | Same seed and replay data give the same results | `[REQUIRED]` |
| Multi-driver tests | Every stop assigned exactly once; fewer-stops-than-drivers and one-stop-driver cases; same assignment across methods | `[REQUIRED]` |
| API tests | Endpoints return expected shapes; long job progress works | `[REQUIRED]` |
| UI smoke checklist (manual) | Generate, run baselines, run evolution in replay mode, view results; empty/error states show correctly | `[REQUIRED]` |
| Live LLM test | One real end-to-end run with a real API key | `[REQUIRED]` (run manually, not in automated tests) |

### 9.4 Results to report

One table (per size bucket and layout): mean and median improvement % vs NN and vs NN + 2-Opt, win/tie/loss counts, valid-candidate rate, runtime per method. Plus: the convergence chart, a sample route map for each method, the best heuristic's code with a plain-language explanation, and the multi-driver comparison.

## 10. Risks and Limitations

### 10.1 Technical risks and practical solutions

| Risk | Why it matters | Practical solution |
|---|---|---|
| LLM returns invalid, malformed, or unsafe code | Wastes calls, could be unsafe to run | Strict output format, parser, layered validation (5.6), limited retries, log the reasons and show the valid-candidate rate |
| Evolved heuristic does not beat NN + 2-Opt | Strong baseline; constructive rules are limited | Treat as a hypothesis (5.7), report honestly, optionally add the labeled Evolved + 2-Opt hybrid |
| Overfitting to training instances | Looks good in training, fails on new data | Train/validation/test split; hidden test set; multiple instance layouts |
| LLM nondeterminism | Runs differ; results hard to repeat | Repeat runs; report mean and spread; save everything; replay mode |
| API cost, rate limits, or outage | Blocks live runs or demos | Small fixed budget, response caching, replay mode, mock LLM for tests, provider chosen via config (several providers allowed by the synopsis) |
| Executing generated code | Security and stability risk | Process isolation, timeouts, no secrets in the child process, optional container (5.6); never run on a shared server |
| Slow candidate evaluation | Makes the loop sluggish | Small instances, per-candidate time limit, O(n) scoring guideline, background job with progress |
| Scope creep from multi-driver, capacity, time windows | Threatens the core deliverable | Finish the CLI milestone (step 7) first; capacity/time windows stay optional |
| Dashboard takes more time than the research | The grade is on the engine and results | Engine first as a CLI; dashboard reads saved results; Streamlit fallback |
| AI-assisted coding introduces hidden bugs | Wrong costs would invalidate results | Tests before features for the cost function, baselines, harness, validator; review every diff; anchor test (5.1) |
| Secrets leak into Git or logs | Key compromise | `.env` in `.gitignore`; never log keys; keys never passed to the sandbox process |
| Beginner-friendliness vs correctness | Complex code is hard to explain in a viva | Ask Kiro for beginner-level explanations; keep modules small |

### 10.2 Known limitations (state these in the report)

- **Synthetic data and Euclidean distance**: results do not directly transfer to real road networks, one-way streets, or traffic.
- **No live traffic, no GPS, no real-time rerouting**: planned routes only.
- **Small benchmark and small budget**: a handful of generations and small instances; findings are indicative, not general proof.
- **Single objective**: only total distance is optimized. Balance across drivers is measured, not optimized.
- **Heuristic scope**: the evolved function only scores the next stop. It cannot discover entirely new algorithm structures.
- **Multi-driver is a simple two-stage method**: the assignment rule is not evolved and is not guaranteed optimal.
- **LLM dependency**: the quality of evolved heuristics depends on the chosen runtime model, and results may differ with another model.

### 10.3 Points the reviewer is invited to challenge

1. Is the single-route evolution plus multi-driver layer (1.5, section 6) a sensible reading of the synopsis and the PPT?
2. Is the scoring-function contract (5.1) expressive enough for the LLM to find something better than NN?
3. Is the train/validation/test protocol and 3-run repetition (5.2, 9.2) enough to claim a fair comparison?
4. Are the safety layers in 5.6 appropriate for a local academic demo, and is anything essential missing?
5. Is the build order in 4.1 realistic for the remaining time, and should any `[REQUIRED]` item be downgraded to `[OPTIONAL]`?
